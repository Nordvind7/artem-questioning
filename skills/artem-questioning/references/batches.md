# Пакетная работа с вопросами

Открой этот файл для большого исследования, диагностики или штурма. Малые ветки можно пройти сразу. Скрипт ведёт очередь в локальном JSON. Интерпретация источников и выбор решения остаются за агентом.

## Начать и продолжить

Храни один JSON в существующей рабочей папке задачи. На него можно сослаться в её брифе или `work/task-state.md`. В командах ниже переменная `SKILL_DIR` указывает на каталог открытого `SKILL.md`. Рабочий каталог содержит файлы задачи.

Файлы пакетных входов и исходные выборки остаются в той же рабочей папке. Не загружай полный JSON обратно в контекст.

```sh
python3 "$SKILL_DIR/scripts/questions.py" work/questions.json add packet.json
python3 "$SKILL_DIR/scripts/questions.py" work/questions.json plan
python3 "$SKILL_DIR/scripts/questions.py" work/questions.json record results.json
python3 "$SKILL_DIR/scripts/questions.py" work/questions.json show Q1 Q2
python3 "$SKILL_DIR/scripts/questions.py" work/questions.json conclude conclusions.json
python3 "$SKILL_DIR/scripts/questions.py" work/questions.json review
```

Для `add` и `record` можно передать `-` вместо имени входного файла и подать JSON через stdin. `plan` показывает ближайшие пакеты, их размеры и несколько готовых вопросов. Для одного большого пакета используй `plan --batch ИМЯ --size 12 --offset 0`. Получи его данные один раз и обращайся к тому же артефакту при разборе следующих порций. При продвижении по очереди после `record` начинай с нулевого смещения, поскольку записанные вопросы уходят из выдачи.

При повторной проверке того же вида плана передай `plan --since ОТПЕЧАТОК`, где отпечаток — поле `fingerprint` из предыдущего вывода. Идентичный план вернёт только `unchanged` и отпечаток. Любое изменение отображаемых вопросов, статусов, прогнозов или охвата вернёт полный текущий план. Используй сравнение, пока предыдущий вывод доступен. После переноса задачи или потери контекста получи план без `--since`.

## Сформировать пакет

`add` принимает массив вопросов. Поля `question`, `decision`, `check` короткие. `batch` обозначает одну выборку, документ, трассировку или другой материал, который можно получить общей операцией. Задай разные имена для разных периодов, сегментов и версий, если ими определяется ответ. `priority` равен `0` у главных стартовых вопросов, `1` у вопросов к решению и `2` у разведки. Главные вопросы проходят первыми. У дочернего вопроса поле `parent` содержит ID вопроса с записанным сбоем или открытым пробелом. Точные повторы в одной ветке и одном пакете объединяются. Близкие формулировки сверяй по тому, одинаковы ли проверка и последующее решение.

```json
[
  {"id":"Q1","priority":0,"batch":"CRM и цели за согласованный период","question":"Действительно ли обращений ноль?","check":"Сверить реальные обращения по всем входам с событиями отчёта","decision":"Исправить учёт или изучить этап потери"}
]
```

В большой задаче формулируй вопросы к нескольким независимым условиям. После ответов развивай ветки со сбоями и решающими пробелами. У одной ветки могут появиться десятки дополнительных вопросов. Из готовых к проверке выбирай те, у которых разные возможные ответы ведут к разным действиям. Сохрани необычную версию, если она проверяема и может перевернуть вывод. Для творческого штурма используй разные механизмы, контрпримеры и разные моменты пути человека.

Если проверке нужны ответы из нескольких веток, укажи `requires` с их ID. Сначала добавь вопросы-предпосылки, потом зависимый. `parent` обозначает происхождение, `requires` обозначает обязательные ответы. Зависимый вопрос появится в готовом пакете после результатов `pass` или `issue` по всем предпосылкам. `plan` показывает, чего не хватает. Новое свидетельство в предпосылке открывает её зависимые вопросы снова и сохраняет старые ответы в истории.

Для вопроса, который должен различить причины, до проверки добавь `predictions`. Это список из двух или более пар `hypothesis` и `expect` с различимым ожидаемым наблюдением. Например, при сломанном переходе контрольное нажатие воспроизводит сбой, а при слабом предложении контрольный переход работает и люди редко нажимают. При записи результата `pass` или `issue` укажи `observed` вместе с источником. Отчёт показывает прогнозы рядом с наблюдением. В глубоком разборе нужна хотя бы одна такая выполненная проверка. При недостатке данных укажи предел и покажи частичный результат.

## Записать результат

`record` принимает массив ответов. `pass` и `issue` требуют наблюдения (`answer`), источника (`source`) и условий проверки (`scope`). `issue`, `unknown` и `deferred` требуют `next`. Для `unknown` укажи, какой факт изменит решение. Для `deferred` укажи, когда вернуться. Статус `open` с причиной в `answer` возвращает вопрос в очередь. Проверка, которая прошла, исключает потомков из плана. Скрипт сохраняет прежний результат при изменении статуса.

```json
[
  {"id":"Q1","status":"issue","answer":"Два обращения из мессенджера отсутствуют в отчёте","source":"work/lead-reconciliation.csv, строки 8–9","scope":"одна кампания и согласованный период, анонимизированные ID","next":"Сверить фактический источник обращений и событие, которое учитывает отчёт"}
]
```

После пакета выбери следующий вопрос по ответам. В кейсе об услугах психолога одна сверка может прояснить число реальных обращений, шаг потери и источник странных обращений. Если факт меняет решение по рекламе, дочитай исходник до принятия решения. Вероятное объяснение и подтверждённое наблюдение храни раздельно. Используй те же данные для нескольких независимых расчётов.

## Проверить готовность итога

`unexpanded` в плане показывает существенные ветки до первого дочернего вопроса. Выполни `review`, чтобы вернуться к каждому главному вопросу с приоритетом 0. Готовые существенные проверки дают статус `continue`. Если вопрос описывает сбой или пробел и требует итоговой оценки, статус `decide`. При незавершённом разборе команда выводит причины и возвращает код 3.

`conclude` принимает массив с полями `id`, `outcome`, `decision` и необязательным списком `evidence` из ID проверок той же ветки. Для `resolved` нужен проверенный ответ на главный вопрос и хотя бы одно подтверждающее свидетельство. Для `limited` укажи `missing` и `limit`. Запиши точный факт, который изменит решение, и почему его нельзя получить в пределах текущего запроса. При любом новом ответе или вопросе ветки прежний вывод сбрасывается. Повтори `review` после продолжения.

Пример. После фильтра по устройству видно, что пользователи перестали доходить до следующей страницы. Уточнение локализует сбой. Главный вопрос о причине может остаться `unknown`: техническое препятствие, несовпадение намерения и слабое предложение ведут к разным действиям. Если в доступных источниках есть способ их разделить, исследуй его. Если источник ограничен агрегатами, зафиксируй, что сравнил и какие наблюдения ещё нужны для выбора действия. Статус готовности показывает полноту записи, а вывод сверяется с исходными свидетельствами.

## Как распределить между моделями

Ведущая модель ведёт очередь, получает данные, подбирает проверки и обновляет результат. Для типовых расчётов и группировки используй код. Luna и Terra работают по [явно выбранной схеме передачи](luna.md). Когда по вопросу есть ответы обеих моделей, сохрани оба с указанием `model`. Это черновики отдельных источников, которые не меняют факт проверки. Учитывай все токены, стоимость повторной передачи контекста и время ожидания.

К сильной модели передавай отдельную развилку, если есть конфликт свидетельств, риск потери сильной альтернативы или высокая цена ошибки. Передача содержит цель, точный вопрос, два конкурирующих объяснения, короткие факты с путями и решение, которое может поменяться. Её вывод возвращается в ту же очередь. Передача запускается в пределах выбранного пользователем режима работы и разрешённых инструментов.

В карте у главного решения со статусом `resolved` в `evidence` должен быть собственный ID или ID дочерней проверки с предварительными `predictions` и записанным `observed`. Привяжи проверку к главному вопросу при постановке. Факты из других веток используй как источники и, при зависимости от их результата, укажи `requires`. При недостающем факте используй `limited` и опиши, какое наблюдение изменит выбор. Поле `coverage.decision_basis` показывает, выполнено ли это условие. Код проверяет связи записей, смысл вывода сверяет ведущая модель.

Для решающей развилки добавь в каждую пару `predictions` поле `action`: что именно сделаешь при таком наблюдении. При одинаковом приоритете `plan` поднимает готовые вопросы с различающимися действиями. Учитывай стоимость при назначении приоритета. У дешёвых справочных вопросов прогнозы можно опустить.

## Бюджет проверок

Один пакет — один ограниченный цикл получения новых свидетельств: один внешний поиск с чтением до двух подходящих первоисточников, один короткий проход по указанному сценарию или один запрос помощнику. Если поиск выполняет помощник в рамках этого же пакета, учитывай его один раз. Параллельные независимые задания двум помощникам занимают два пакета. Выбери один вопрос, период и материал. В контекст верни наблюдение, условия и ссылку. Подходящий факт из уже доступной выгрузки или сохранённого пакета используй сразу.

Важность определи по смыслу слов пользователя. «Важно не тратить лишнее» описывает ограничение, «это важная задача» повышает запас. В начале важного разбора вызови `effort important`. Обычный режим действует по умолчанию. Повторная установка режима, смена режима, возобновление и второй цикл сохраняют уже занятые места. Продолжай в той же очереди. После каждого пакета назови факт, изменивший развилку. Если два пакета подряд дали только повторы, прекрати расширять поиск по этой версии. Проверь оставшиеся обязательные ветки по имеющимся материалам. Ориентир `question_guide` учитывает оба цикла и допускает явный запрос на другой объём. Оставляй минимум восемь мест на второй цикл, пока основной вывод открыт. Оставшийся бюджет можно не расходовать.

Перед затратной проверкой создай вопрос через `add`, затем зарезервируй пакет с устойчивым ID для его источника, условий и проверки. Пример для известного Q1:

```sh
python3 "$SKILL_DIR/scripts/questions.py" work/questions.json effort important
python3 "$SKILL_DIR/scripts/questions.py" work/questions.json probe mobile-replay Q1 --if-yes "Исправить переход на мобильном" --if-no "Проверить совпадение ожидания с оффером"
```

Только `granted: true` открывает **один** запуск. Повторный ID или исчерпанный запас возвращает код 4. При повторе найди уже полученный результат или дождись текущей проверки. Если предыдущая попытка сорвалась, запиши пробел. Обоснованный повтор по изменённым условиям занимает новое место. `plan` показывает режим и остаток. Несколько вопросов к одной выборке можно проверить за один пакет. Любой более строгий лимит пользователя приоритетен.

При исчерпании бюджета заверши доступные локальные проверки. Укажи первый всё ещё полезный недостающий факт и какое решение он может изменить. Новый проход по тем же данным имеет смысл лишь после значимого изменения факта или условий. В чате без CLI считай пакеты вручную. Это ограничение объёма работы навыка. Точное число токенов зависит от клиента, длины контекста и ответов инструментов.
